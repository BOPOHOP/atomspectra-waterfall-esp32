# Known Issues / Известные проблемы

**🇷🇺 Русская версия** · [🇬🇧 English](KNOWN_ISSUES.en.md)

Список известных багов, ограничений и исправленных проблем AtomSpectra ESP32 Gateway.

## Открытые

### Пароль полевой точки доступа по умолчанию общеизвестен

Пароль полевой точки доступа по умолчанию указан в README и в веб-интерфейсе, то есть известен всем.
Веб-API платы рассчитан на доверенную сеть. Пока полевая точка доступа работает с паролем по умолчанию,
к плате может подключиться любой, кто находится рядом. Смените пароль на свой на вкладке «Система»
(при подключении через точку доступа с паролем по умолчанию вкладка сама об этом предупреждает).
Пересмотр модели угроз «доверенная сеть» — отдельной задачей после 1.2.29.

### Веб-интерфейс замирает на время тяжёлых операций — исправление в 1.2.30

Веб-сервер платы однопоточный: пока один запрос выполняет долгую операцию, остальные вкладки и клиенты ждут.
Найдено внешним аудитом кода (Codeaudit, 29.09), перенесено в 1.2.30 решением владельца проекта.
- LK-02: запросы старта/стопа/очистки ждут замок файлов водопада без таймаута, пока идёт запись. Перезагрузка
  ждёт его с таймаутом: до 5 с, а если открытый сегмент не закрылся с первого раза — до ~11 с суммарно
  (`spectrogram.c:1957-1959`). Удаление сегмента уходит в очередь и замок в запросе не ждёт (#HTTP-FS1 ниже).
- LK-03: «Очистить» водопад удаляет до ~11 сегментов прямо в задаче веб-сервера.
- LK-04: Старт/Стоп записи водопада ждут дописывания строк (до 60 с) и закрытия сегмента внутри запроса.
- LK-05: `/api/settings/backup` и `/snapshot` опрашивают прибор до ~4 с внутри запроса.
- LK-07: `/api/ota/github/check` ходит на GitHub по HTTPS внутри запроса, до 15 с.
- LK-08, P-01: выдачи окна водопада (до 4 МБ), экспорта и сегментов держат веб-сервер всю передачу; каждый
  вход или F5 на странице водопада заново скачивает всё кольцо.
- LK-09: кадры WebSocket по 16 КБ отправляются с ожиданием до 3 с; медленный клиент задерживает всех.
- S-01: тяжёлые GET (`/api/ota/github/check`, `/api/settings/backup`, `/api/waterfall/window`) не требуют
  CSRF-токена и не проверяют Origin: чужая страница, открытая в браузере в той же сети, может их запускать и
  нагружать плату.

### «Сброс» не дописывает последнюю строку водопада — до одного шага записи на сброс

Плата отправляет команду сброса прибору сразу (`handle_reset`, `web_server.c:540`) и строку перед ней не
фиксирует; прибор по команде обнуляет счётчики. Импульсы, накопленные с последней записанной строки до сброса
(не больше одного шага записи, по умолчанию 5 с), в водопад не попадают. На живой плате 30.09 три сброса дали
1, 3 и 5 с (по меткам времени прибора; оценка, не прямой замер потери). Спектр при сбросе очищается намеренно, а в
водопаде эти секунды остаются незаписанными. Исправление — зафиксировать строку до отправки команды — запланировано на 1.2.30.

### Выгрузка журнала отладки временно занимает до ~0.5 МБ памяти — исправление в 1.2.30

Касается только включённого кольца журнала отладки (по умолчанию выключено).
- `GET /api/debug/log` копирует в память всё заполненное кольцо, даже когда запрошены только новые строки
  (`since`): до 384 КБ, плюс буфер отправки ответа (до 64 КБ по настройке lwIP). Замер 30.09 на 1.2.29:
  выгрузка 216 758 Б при свободных 951 068 Б опустила отметку `min_free_heap` до 642 548 Б (пиковое потребление 308 520 Б).
- Если выгрузка совпадёт с автосохранением спектра или нагрузкой на веб-интерфейс, свободная память на
  короткое время опускается ниже 512 КБ (замер: 462 632 Б). Если памяти не хватит, запрос получит
  500 `oom` (`debug_log_ring.c:532`), остальная работа платы продолжится.
- Код выгрузки не менялся с 1.2.21. Исправление (выгрузка частями, копия только новых строк) — в 1.2.30.

### BUG-AS-08: ⚠ Шлюз не резервирует заводскую DSP-настройку прибора

**Статус:** ограничение by design + предупреждение (не баг прошивки шлюза).

Прибор «Atom Spectra» хранит **внутри себя** настройку цифровой обработки импульсов
(DSP-tuning): пороги формы импульса `RISE` / `FALL` / `NOISE`, `MAX` / `HYST` / `MODE` /
`STEP`, частоту дискретизации `F`, аппаратные потенциометры HV/усиления `POT` / `POT2`,
таблицу pile-up и термокомпенсацию.

Бо́льшая часть этих значений видна в ответе прибора на команду `-inf` — включая таблицу
pile-up (`PileUp […]` / `PileUpThr`) и таблицу термокомпенсации **MAX** (`Tco […]`). **Но
таблица термокомпенсации baseline** (зависимость `POT2` / `V` от температуры, точки
`-t_pot`) **в `-inf` НЕ возвращается** — там присутствует лишь флаг `TCpot ON/OFF`. Полный
слепок baseline-термокомпенсации даёт отдельная команда **`-tc_pot?`**.

**Что наблюдалось.** Зафиксирован случай, когда у прибора **обнулилась вся эта настройка**:
`-inf` стал отдавать `RISE 0 FALL 0 NOISE 0 F 1.00 MAX 0 HYST 0 ... POT 0 POT2 0` при том,
что сам прибор остаётся на связи и отвечает `VERSION`. С нулевыми порогами прибор физически
не выделяет импульсы — счёт пропадает (`total_counts = 0`, `cps = 0`), хотя соединение
USB/CDC исправно. **Переподключение USB настройку НЕ восстанавливает.**

**Влияние:** до восстановления DSP-настройки прибор не набирает спектр (ноль отсчётов).
Шлюз, WiFi, веб-интерфейс, TCP-мост и **energy-калибровка** (полином `E(ch)`, хранится
на шлюзе в `calib.bin`) при этом **не затронуты** — это состояние самого прибора, а не
прошивки шлюза.

**⚠ Предупреждение — НЕ восстанавливать «вслепую» командами тюнинга.**
Хотя протокол прибора имеет команды настройки (`-ris`, `-fall`, `-nos`, `-max`, `-hyst`,
`-U`, `-V`, `-step` и др.), **записывать их наугад нельзя**:
- `POT` / `POT2` — аппаратные потенциометры HV/усиления, **индивидуальны для каждого
  экземпляра** детектора. Чужие значения (в т.ч. из примеров в документации) могут задать
  неверное смещение/усиление и повредить прибор.
- Корректные значения порогов и HV знает только заводская процедура калибровки под
  конкретный экземпляр.

**Обходной путь / восстановление:** обратиться к **производителю прибора (KB Radar)** —
восстановление заводского профиля детектора выполняет производитель. Самостоятельно,
«вслепую» записывать параметры настройки нельзя (см. предупреждение выше).

**Рекомендация на будущее:** шлюз умеет **читать** `-inf` (показывает поля в Web UI), но
не делает их резервную копию. Имеет смысл при настроенном приборе один раз сохранить **два**
ответа прибора как эталонный «слепок» DSP-конфигурации:

1. ответ на **`-inf`** — основные пороги, `POT` / `POT2`, таблицу термокомпенсации MAX
   (`Tco […]`) и pile-up;
2. ответ на **`-tc_pot?`** — таблицу термокомпенсации baseline (`POT2` / `V` от
   температуры); **её в `-inf` нет** (см. выше).

Тогда повторный сброс можно будет зафиксировать и передать производителю (KB Radar) оба
слепка как референс заводской настройки.

**Реализовано в v1.2.28.** Рекомендация выше выполнена: кнопка «Сохранить слепок настройки
прибора» на странице «Сервис» — `POST /api/settings/snapshot` сохраняет оба ответа (`-inf`
и `-tc_pot?`) на LittleFS с меткой времени; `GET /api/settings/snapshot` отдаёт последний
сохранённый слепок БЕЗ повторного обращения к прибору (важно, если DSP-настройка сломалась
именно сейчас — POST её не перезапишет битым чтением). `main/web_server.c:2072-2238`
(`handle_settings_snapshot`, `handle_settings_snapshot_get`), `web/service.html` и
`demo/service.html` (кнопка + ссылка «Скачать последний слепок»). Сам корневой дефект
(обнуление настройки прибором) остаётся ограничением прибора — слепок лишь ускоряет
восстановление через производителя, не устраняет причину.

### BUG-AS-03: Серийный номер не считывается

**Статус:** смягчено в v1.2.29 (корень — усечённый ответ прибора на `-cal` — не подтверждён на живом приборе).

**v1.2.29.** Запрос `-cal` перед стартом набора делается, пока пуста калибровка ИЛИ серийник
(`calib_autoread_needed`, `main/calib_autoread.h:110-113`), — смягчение 1.2.28 больше не
разовое. Если калибровка на плате уже задана (в том числе вручную), ответ на такой запрос
обновляет только серийник, коэффициенты прибора не применяются (`calib_apply_coeffs`,
`main/calib_autoread.h:118-121`; флаг запроса — `main/usb_host_cdc.c:1021`, срок 5 с). Ручное
«Считать» по-прежнему применяет калибровку прибора. Абзац «Смягчено… в v1.2.28» ниже описывает
прежнее поведение.

Серийный номер прибора (`serial_number`) остаётся пустым после подключения.

**Причина (текст уточнён в 1.2.28 — прежняя формулировка смешивала `-inf` и `-cal`).**
Серийник парсится ИСКЛЮЧИТЕЛЬНО из дампа `-cal` (40 строк: калибровка + CRC + серийник в
строке 39, 0-индекс) — НЕ из `-inf`. `-inf` и `-cal` различаются по содержимому (`-inf`
несёт ключ `VERSION `, `-cal` — нет) и обрабатываются одной и той же функцией
`spectrum_process_info_response()`; ветка серийника — `main/spectrum.c:558-573`, гейт
`if (!is_inf)` — `main/spectrum.c:474`. Причина пустого серийника — ответ прибора именно
на `-cal` короче 40 строк; калибровка (строки 0–10 того же дампа) при этом по-прежнему
читается корректно.

**Смягчено, но НЕ устранено в v1.2.28.** Автосчитывание калибровки перед стартом набора
(#AWF-12) шлёт `-cal`, пока калибровка не задана — если оно один раз успешно пройдёт,
серийник заполнится тем же путём. Смягчение разовое: как только
`spectrum_calibration_is_missing()` становится ложным, повторные старты `-cal` больше не
запрашивают (`main/usb_host_cdc.c:982-983`, `main/calib_autoread.h:99-109`), и у серийника
не остаётся автоматических попыток обновиться, пока калибровка не будет сброшена заново.
Для стартов через TCP-мост автосчитывание не работает вовсе (см. F3 ниже). Корень (реально
усечённый ответ прибора на `-cal`) статическим чтением кода не проверяется — нужен прибор,
дающий укороченный `-cal`, чтобы подтвердить или опровергнуть находку.

**Влияние:** в Web UI, XML и CSV экспорте поле серийного номера пустое. Функциональность спектрометра не затронута.

**Обходной путь:** серийный номер можно задать вручную через Web UI (панель калибровки).

### issue #52: резервный снимок пишется в случайной фазе приёма USB

**Статус:** ограничение по замыслу (v1.2.23)

Автоматический снимок спектра (33 КБ на LittleFS) записывается по срабатыванию периода, без
привязки к концу свипа — в отличие от автосохранения `current.bin`, которое ждёт коммита свипа
(#FW-13), чтобы попасть в тихое окно USB. Запись на flash замораживает кэш обоих ядер, поэтому
снимок может стоить одного отброшенного свипа (`histogram sweep dropped`).

**Почему так:** автосохранение идёт раз в минуту, снимок — раз в часы (минимум 1 час). Цена —
до одного свипа из ~3600 в час; сложность фазовой привязки того не стоит. Снимок берётся под
`http_io_gate` (как кнопка «Сохранить») и под `flash_quiet_writer_lock` (как autosave и запись
сегментов водопада), поэтому с другими писателями LittleFS он не конкурирует — не привязана
только ФАЗА относительно свипа.

**Влияние:** пренебрежимая потеря полноты набора. Если период выставлен в минуты (стендовый
ключ `backup_test_minutes` в `/api/boot-config`, в Web UI его нет), потери станут заметны —
режим предназначен только для проверки, не для измерений.

### Сторож набора не действует после команд TCP-клиента и после `-sta` с параметрами

**Статус:** ограничение по замыслу (v1.2.23)

С v1.2.23 шлюз замечает, что набор встал сам (например, после перезагрузки прибора): если
последней его командой был «Старт», а гистограмм нет 20 с, он повторяет `-sta` (не чаще раза в
20 с; счётчик — `acq_resend_count` в `/api/usb-diag`). До v1.2.23 такой простой не замечался:
RX-сторож видел непрерывный 2-байтовый статус FTDI и считал связь живой. Кнопка «Перезагрузить
прибор» перед командой сама отмечает «набор идёт», если гистограммы шли.

Сторож молчит, если шлюз не знает, запущен ли набор намеренно:
- после ЛЮБЫХ байтов от TCP-клиента (приложение AtomSpectra через TCP-мост) — и после его
  отключения, до следующей команды «Старт» из самого шлюза;
- после `-sta` с параметрами (`-sta 60`, `-sta -s`): ограниченный по времени или «тихий» набор
  останавливается или молчит по замыслу, и повтор голого `-sta` его бы сломал;
- после «Стоп» — иначе сторож перебивал бы остановку пользователем.

Набор, запущенный не шлюзом, сторожем тоже не охраняется.

### AWF-3: редкие случаи двойного счёта или задержки при сбросе прибора

**Статус:** ограничение (v1.2.24)

«База» (см. раздел «Спектр после отключения питания» в README) в норме сохраняет спектр без
потерь. В двух редких сочетаниях возможна неточность: (1) если после реального сброса прибора
пакет времени приходит с задержкой больше нескольких секунд ИЛИ отставание держится первые
секунды новой сессии — счёт в этом узком окне может однократно удвоиться; (2) при одновременной
записи двух сохранений базы подряд на flash может на короткое время остаться версия старее той,
что в памяти (переживёт следующую запись). Оба случая не теряют данные необратимо и не влияют
на обычную работу.

### #AWF-12b: «Считать» не применяет нулевой или NaN-дамп калибровки (F12)

**Статус:** ограничение по замыслу (v1.2.28).

С `v1.2.28` дамп `-cal` с CRC-валидными, но нулевыми или нечисловыми (NaN/Inf) коэффициентами
считается «калибровка не задана», как и CRC-невалидный дамп — не перезаписывает текущую
калибровку платы. Это относится и к ручному «Считать», и к автосчитыванию перед стартом
набора. Отличить «дамп пришёл, но проигнорирован» от «дамп не пришёл» можно по `/api/device`
(`calib_set`) и по логу команд.

**UI-индикация добавлена в v1.2.28 (F12/RO1).** Раньше отклонение дампа было видно только по
`/api/device`; теперь кнопка «Считать» на страницах «Спектр» и «Сервис» сверяет счётчик
`calib_reject_seq` (`/api/device`) до и ~900 мс после запроса и, если он вырос, выводит в
лог-панель `cal.readEmpty` («прибор вернул пустую калибровку (нули/NaN) — калибровка платы
не изменена»). Счётчик — `main/spectrum.c:90,548,1196` (бампается под тем же `SPEC_LOCK`,
что и сам блок отклонения), поле в ответе — `main/web_server.c:1746`, чтение в UI —
`web/index.html:690-698`, `web/service.html:337-344` (+ demo-зеркала). Само поведение
(не перезаписывать) не менялось — добавлена только видимость.

### #AWF-12b: TCP-мост не запрашивает калибровку перед `-sta` (F3)

**Статус:** ограничение по замыслу (v1.2.24+).

Автосчитывание калибровки перед стартом набора (если она не задана) срабатывает только для
`-sta`, отправленного самим шлюзом (кнопка «Старт», авто-возобновление после реконнекта/ребута,
повтор сторожа). Команда `-sta`, пришедшая от TCP-клиента (AtomSpectra/BecqMoni через мост,
порт 8234), идёт к прибору сырым путём в обход этой точки — намеренно: мостом управляет внешнее
приложение, и вставка своей команды в чужой поток исказила бы протокол ПК-программы.

## Исправленные

### Обновление прошивки по Wi-Fi теряло до минуты строк водопада — ИСПРАВЛЕНО (v1.2.29)

**Было.** При обновлении прошивки (вручную и с GitHub) плата перезагружалась, не закрыв открытый сегмент
водопада. Строки, записанные после последнего сброса сегмента во flash (раз в 60 с), пропадали: сегмент
оставался, но короче. Остальные штатные перезагрузки сегмент закрывали.

**Стало.** Перед перезагрузкой после обновления плата закрывает сегмент так же, как при других штатных
перезагрузках. Если flash занят, повторяет до 6 раз и пишет ошибку в журнал, если не вышло. Вкладка
«Система» сообщает о конце установки только после этой подготовки. Замер обновлением в середине
минутного окна: до исправления потеряно 10 строк, после — 0.

### Первая строка водопада после перезагрузки платы считала импульсы дважды — ИСПРАВЛЕНО (v1.2.29)

**Было.** После перезагрузки при идущей записи первая строка водопада считалась от автоснимка спектра,
который бывает старше последней строки до минуты. Импульсы, уже записанные в последние строки перед
перезагрузкой, попадали в первую строку ещё раз (замер: лишние 5905 импульсов в одной строке).

**Стало.** Перед штатной перезагрузкой плата сохраняет опору последней строки (`/storage/wf_ref.bin`)
и после загрузки считает первую строку от неё. Файл годен только для следующей загрузки и проверяется
контрольной суммой. Если файла нет (обрыв питания, сбой), первая строка не пишется, опора переносится
на первый живой снимок. Замер после исправления: расхождение −170 импульсов, в пределах шума.

### «Сброс», не выполненный прибором, терял импульсы в водопаде — ИСПРАВЛЕНО (v1.2.29)

**Было.** Если прибор не выполнил «Сброс», плата примерно через 10 с показывала набор прибора, а водопад переносил
опору без строки. Импульсы между последней строкой до «Сброса» и этим моментом пропадали (наблюдалось
4718 и 2826 импульсов).

**Стало.** Если набор прибора продолжает последнюю строку (ни один канал, сумма и время не уменьшились),
прибор данные сохранил, и плата пишет строку против последней строки до «Сброса». Иначе — прежний
перенос опоры без строки: против чужого набора строка дала бы скачок. Проверено host-тестом
`tests/host/test_wf_rst_keep.c`; живьём не воспроизводилось, для этого нужен «Сброс» спектра.

**Остаётся.** Если прибор в этой сессии перезапускался (плата хранит базу набора до перезапуска), а потом
«Сброс» не подтвердился, импульсы этого интервала по-прежнему теряются (без скачка).

### issue #58: спектр не показывался после перепрошивки или перезагрузки при идущем наборе — ИСПРАВЛЕНО (v1.2.29)

**Было.** После перепрошивки или перезагрузки платы при идущем наборе спектр не показывался, пока
прибор сам не обнулит время набора. «Сброс», который прибор не выполнил (команда не дошла или
отвергнута), так же замораживал спектр.

**Стало.** После «Сброса» плата ждёт от прибора подтверждения (время набора с нуля) около
10 с от первого отклонённого пакета, по расчёту 11–13 с после команды (`SPECTRUM_RESET_CONFIRM_TIMEOUT_S`, `main/spectrum_base_plan.h:172`), затем показывает

пишет строку в журнал главной страницы. Первый коммит после сброса принимается только по пакету
времени, пришедшему после сброса в том же сеансе USB (`spectrum_stat_tag_usable`,
`main/spectrum_base_plan.h`). В водопаде и на «Мониторинге» при этом не появляется точка со всем
накопленным набором прибора. Проверено мутационно: `tests/host/mutate_issue58.sh`, 15 мутантов.

### «Сброс» и перезагрузка в течение ~1 мин возвращали спектр до сброса; «Сброс» при отключённом приборе — ИСПРАВЛЕНО (v1.2.29)

**Было.** Если после «Сброса» плата перезагружалась или теряла питание раньше следующего
автосохранения (около минуты), она поднимала спектр, набранный до сброса (из автоснимка или
незавершённого `.tmp`). «Сброс» при отключённом приборе очищал только плату.

**Стало.** «Сброс» создаёт метку `reset.mark` (`reset_mark_create`, `main/spectrum.c:775`);
при метке восстановление после загрузки ничего не поднимает, метку снимает первое автосохранение
нового набора. Если команда `-rst` не дошла до прибора, метка помечается «не доставлено», и плата
повторяет `-rst` при следующем подключении прибора — в том числе после своей перезагрузки
(`main/usb_host_cdc.c:564`, функция — `:602`). Повтор отменяется, если за это время был новый «Сброс».

### #HTTP-FS1: веб-интерфейс замирал до 5 с, когда сборщик подтверждал приём сегмента — ИСПРАВЛЕНО (v1.2.29)

**Было (v1.2.28 и раньше).** Подтверждение приёма сегмента (`POST /api/waterfall/segment/delete`, его шлёт
сборщик pull после скачивания) выполнялось прямо в задаче веб-сервера: она ждала окна записи во flash

однопоточного веб-сервера.

### #FW-50: зависание web-интерфейса (водопад + мониторинг) — ИСПРАВЛЕНО (v1.2.29)

**Причина.** Буферы Wi-Fi и TCP/IP-стека размещались во внутренней RAM; под нагрузкой (несколько
вкладок, водопад, мониторинг) она исчерпывалась до сотен байт, и веб-интерфейс переставал отвечать
при общем свободном heap ≈700 КБ (почти весь — PSRAM).

**Исправление.** `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` в `sdkconfig.defaults` — буферы
размещаются в PSRAM; число буферов Wi-Fi закреплено в `sdkconfig.defaults`, чтобы чистая сборка
совпадала с проверенной. В `/api/system` добавлены поля внутренней RAM: `int_free`, `int_largest`,
`int_min`, `int_dflt_free`, `int_dflt_largest`, `heap_walk_us`. A/B-замер под нагрузкой: без опции
0 из 56 ответов, с опцией 2224 из 2224.

**Наблюдение (2026-07-27):** плата в LAN перестала отвечать около ночи при включённых
водопаде и мониторинге; позже истёк dhcp lease from ap. AtomSpectra по USB не
перезагружали — спектр на приборе сохранился. Другие клиенты той же сети были живы →
не AP. **Не** путать с закрытым **#FW-13** (LittleFS autosave freeze / UART CDC blocking)
и с закрытым **#FW-8 residual** (гистограммные drops от autosave — sliced quiet write, 2026-08-12).

**Инструмент диагностики (остаётся в прошивке):** Сервис → Debug-лог (NVS `dbglog`); кольцо
384 KiB PSRAM; забор дампа внешним сборщиком. Default **off**.

**Стоимость по flash** (ESP-IDF 5.4.2, `esp32s3`, чистый `sdkconfig` от
`sdkconfig.defaults`, замер `atomspectra_gw.bin`):

| Сборка | Размер | Δ к базе |
|---|---|---|
| база (`v1.2.2`) | 1 486 112 B | — |
| кольцо без `CONFIG_LOG_MAXIMUM_LEVEL_DEBUG` | 1 494 128 B | **+8 016 B** (≈7.8 KiB) |
| кольцо как есть (`v1.2.3`) | 1 530 848 B | **+44 736 B** (≈43.7 KiB) |

То есть сам код кольца стоит ≈8 KiB, а остальные ≈36 KiB — это строки `ESP_LOGD`
по всему ESP-IDF, которые перестаёт вырезать компилятор при
`CONFIG_LOG_MAXIMUM_LEVEL_DEBUG=y`. Без этого флага кольцо соберётся, но
DEBUG-строк в нём не будет. Само кольцо 384 KiB живёт в PSRAM и на flash не влияет.

**Контракт эндпоинтов кольца:**

| Эндпоинт | CSRF | Зачем |
|---|---|---|
| `GET /api/debug/log/meta` | нет | только счётчики/настройки кольца (`enabled`, `level`, `next_seq`, `dropped`, `lost_busy`, `gen`, `fill_pct`) — без `fw_version`/uptime/heap; это гигиена, не auth (`/api/system` рядом по-прежнему открыт) |
| `GET /api/debug/log?since=N` | **да** | в дампе видны SSID, IP и URL выгрузки |
| `POST /api/debug/log/flush` | **да** | мутирующий запрос |
| `GET/POST /api/debug/log/config` | POST — да | как остальные настройки |

`GET` с обязательным заголовком — намеренно: сторонняя страница, открытая в том же
браузере, не может прочитать токен (same-origin policy), значит не сможет и вычитать
лог с адреса пользователя. Порядок для любого внешнего сборщика:

```sh
TOKEN=$(curl -s http://<board>/api/csrf-token | sed 's/.*"token":"\([^"]*\)".*/\1/')
curl -s -H "X-CSRF-Token: $TOKEN" "http://<board>/api/debug/log?since=0"
```

**Уровни (`level` в настройке) — лестница по кругу тегов, не только по глубине:**

| Уровень | Что попадает в кольцо |
|---|---|
| `standard` | `*` = WARN + свои теги (`main`, `wf`, `web`, `http_io`, …) на INFO |
| `detailed` | то же + системные теги сети на INFO (`httpd*`, `wifi*`, `dhcpc`/`dhcps`, `lwip`) |
| `debug` | то же + DEBUG у самых горячих своих тегов (`usb_cdc`, `spectrum`, `wf_ofl`) |

**Что кольцо НЕ поймает.** Буфер живёт в PSRAM и не переживает перезагрузку:
после паники, WDT-ресета или пропадания питания дамп пуст, а `gen` начинается
заново. Инструмент рассчитан именно на гипотезу soft-lock — плата жива и
отвечает по HTTP, но интерфейс не работает; для сценария «ушла в панику и
перезагрузилась» нужен coredump, а не это кольцо. Строки, отброшенные из-за
занятого мьютекса, считаются отдельно от вытесненных по кругу и видны как
`busy=` рядом с `drop=` (Сервис → Debug-лог) и как `lost_busy` в
`/api/debug/log/meta`: «лога не было» и «лог потерян в интересный момент» —
разные исходы, и путать их при разборе зависания нельзя.

### #AWF-12b: теоретические последовательности пакетов дампа/ответов прибора (R2/R3) — ИСПРАВЛЕНО (v1.2.28)

Разбор текстовых ответов прибора (`main/text_accum.h`) искал начало дампа `-cal` только с
позиции 0 в накопителе, а копирование пакета (`text_accum_feed`) не обрабатывало байт `\0`
внутри пакета — оба дефекта были гипотетическими (ни разу не наблюдались в логах контура),
но код был уязвим: однострочный посторонний hex-ответ перед дампом, дамп короче 9 байт первым
кадром или `-ok`+дамп одним кадром увели бы разбор на неверное смещение (CRC не сойдётся,
калибровка не применится), а `\0` внутри пакета маскировал бы все последующие текстовые ответы
до переполнения аккумулятора (~4 КБ, ≈2 ч при опросе раз в 30 мин).

С v1.2.28 (`fadde1c`, sweep-C): `text_accum_find_cal_window()` сканирует весь аккумулятор
байт-за-байтом и ищет 10 строк коэффициентов + валидную по CRC32 строку CRC —
`main/text_accum.h:52-118`; `\0` внутри пакета заменяется на пробел при копировании
(`main/text_accum.h:332-336`, было — голый `memcpy`); `main/usb_host_cdc.c:160-165` (через
`text_accum_dispatch()`, `main/text_accum.h:443-460`) передаёт
в `spectrum_process_info_response()` найденное окно, а не всегда позицию 0. Проверено на
боевой фикстуре (реальный дамп `REAL_DUMP_110` из `.logs/cal_capture.txt`, CRC32 сверен
независимо `zlib.crc32`) и мутационно — 4/4 мутанта убиты. Живых
повторов этих последовательностей по-прежнему не было — правка закрывает уязвимость кода, а
не наблюдавшийся инцидент.

**Дробление дампа и потеря кадра (раунд 3 разбора 1.2.28).** Если прибор отдаёт дамп `-cal`
несколькими кадрами и последний кадр теряется, следующий дамп мог «дописать» прежний до 40 строк —
серийник брался из чужой строки. Теперь накопитель помнит начала пакетов (`text_accum_marks_t`,
`main/text_accum.h:241-245`): если в хвосте дампа на границе строки начался пакет, а CRC-окно
возможного нового дампа ещё не пришло целиком, серийник не берётся, пока не решит следующий
пакет или секунда тишины (`TEXT_ACCUM_QUIET_MS`, `main/usb_host_cdc.c:253-259`); новый дамп с тем
же началом распознаётся сразу. Цена — у дампа, чей последний кадр начинается на границе строки,
серийник приходит с задержкой до ~1 с. Остаётся: (1) двойная потеря (у прежнего дампа потерян
последний кадр, у следующего — все кадры после первого) вместе с перекалибровкой прибора между
двумя `-cal` даёт неверный серийник до следующего полного `-cal`; (2) посторонний ответ в одном
кадре с началом дампа короче 110 байт по-прежнему теряет этот дамп, как в 1.2.27 и ae667ba
(калибровка не применяется, автозапрос `-cal` повторится). Размер кадров дампа на живом приборе
не снят; наблюдались только целые Text(400).

### #FW-63: открытый сегмент терялся ЦЕЛИКОМ при аварийном сбросе — ИСПРАВЛЕНО (v1.2.17)

Закрывает пробел, оставленный **P-016** ниже: тот фикс защищал только штатные пути
перезагрузки, аварийные (потеря питания, прошивка извне, panic) — нет.

Сброс метаданных открытого сегмента на носитель выполнялся по условию «каждые N строк **и**
только пока прибор не подключён по USB». Вторая половина условия обнуляет первую в реальной
эксплуатации: прибор подключён всегда, пока идёт измерение. Расчёт был на то, что обычного
сброса буфера (`fflush`) достаточно для обновления размера файла в файловой системе — это
неверно, `fflush` не обязывает файловую систему обновить служебную запись о размере на
носителе, это делает `fsync`. При аварийном сбросе такой сегмент читался как файл нулевого
размера, хотя заголовок в него записывался, и терялся целиком.

Сегмент закрывается по возрасту (10 мин), а не по числу строк: при боевом интервале 180 с
за это время накапливается 3–4 строки из 64 возможных. Значит аварийный сброс стоил **до
десяти минут измерений** за раз.

Фикс: метаданные сбрасываются на носитель не реже раза в минуту, независимо от того,
подключён прибор или нет. Проверено на живой плате red-green: до фикса внезапный сброс при
1 строке в сегменте стирал его целиком (счётчик потерь рос); после фикса тот же сброс при
3 строках — сегмент выжил (3 строки, 86 102 Б), счётчик не изменился. Цена фикса замерена
(10 мин покоя, одинаковые условия до/после): потери свипов 0,00 % в обоих случаях, ни
одного сброса метаданных дольше 100 мс.

### #MON-2: мониторинг CPS показывал пустой график, пока не нажат «Старт» — ИСПРАВЛЕНО (v1.2.16)

Плата (`#MON-1`) собирает секундные отсчёты в кольцо PSRAM автономно и непрерывно, вне

### P-016: открытый сегмент терялся при штатной перезагрузке — ИСПРАВЛЕНО (v1.2.12)

При перезагрузке через веб-кнопку, смену WiFi или точки доступа последний открытый сегмент
водопада мог потеряться целиком, даже если данные уже физически лежали на флеш: LittleFS
не обновляет размер файла в inode без явного `fsync`/`fclose`, и проверка целостности при
следующем старте отбраковывала такой файл как пустой. В худшем случае (боевой интервал
180 с) это до 3,2 часов измерений на одну перезагрузку.

Фикс: перед всеми штатными путями перезагрузки прошивка теперь принудительно дописывает и
закрывает открытый сегмент. Аварийные пути (потеря питания, panic, watchdog) этим фиксом
не покрыты — там сегмент по-прежнему может потеряться.

> **Обновление (v1.2.17):** пробел на аварийных путях закрыт — см. **#FW-63** ниже.

### #DATA-7: тихая потеря данных сборщиком при переиспользовании имён сегментов — ИСПРАВЛЕНО (v1.2.9 + wf-recorder v0.3.0)

Имя файла сегмента (`seg_NNNNN.aswf`) уникально только в пределах текущего наполнения
каталога: после `clear`, ребута на пустом каталоге или стирания NVS нумерация начинается
заново, и новый сегмент получает имя уже забранного. Клиент `wf-recorder` ≤ v0.2 опознавал
сегмент по паре (имя, размер) — при фиксированном интервале все полные сегменты весят
одинаково, поэтому новый сегмент принимался за уже вшитый: подтверждение удаления уходило
**без записи данных**. У реального пользователя так безвозвратно пропали 66 сегментов
(~13 ч измерений) — разбор в
[wf-recorder#1](https://github.com/VibeEngineering-LLC/wf-recorder/issues/1).

Исправление двумя сторонами: прошивка `v1.2.9` отдаёт в листинге `seg_seq` и `started_at`
из шапки файла; клиент `v0.3.0+` опознаёт сегмент по SHA-256 тела и не подтверждает
удаление до подтверждённой записи. Фикс проверен четырьмя независимыми воспроизведениями,
включая непреднамеренное (имя переиспользовано в обычной работе — клиент корректно скачал
заново). Подробности: `docs/bugs/2026-08-15-fw8-unreachable-and-503.md`.

### #FW-51: `CDC_ACM_HOST_ERROR` → тихий stall анализатора (нет reconnect / нет тревоги)

**Статус:** код + HW verify — **PASS** 2026-08-05; soak на `v1.2.5`. Release notes:
[`docs/releases/v1.2.5-fw51-fw43-hotplug.md`](docs/releases/v1.2.5-fw51-fw43-hotplug.md).
Write-up: [`docs/bugs/2026-08-05-cdc-host-error-silent-stall.md`](docs/bugs/2026-08-05-cdc-host-error-silent-stall.md).

**Было:** после `CDC error` без `Device disconnected` handle оставался non-NULL →
false-green `analyzer_connected` / `usb_connected`, counts freeze, reconnect не
запускался. `#FW-43` `spectrometer_dead` при `rx_age≥4s` специально возвращал false.

**Исправление (`main/usb_host_cdc.c` + diag JSON):**
1. `cdc_teardown(reason)` — единый close+null+`cdc_open=false` (claim под mutex).
2. `CDC_ACM_HOST_ERROR` → teardown (`error`), как disconnect.
3. RX watchdog / bus-empty в `usb_connect_task` (arm window, затем stale RX или
   `bus_devs_now==0`) → тот же teardown. ARM (10 s) должен быть **&lt;** WD (15 s).
4. `usb_host_cdc_is_connected()` требует свежий RX после grace 5 s (не handle alone).
5. `/api/usb-diag`: `cdc_error_count`, `rx_watchdog_trips`, `bus_empty_trips`,
   `reconnect_ok`, `last_fault_reason` / `last_fault_ts_ms`.

**HW verify:** unplug → `last_fault=disconnect`, `reconnect_ok≥1`, live again.

**Следом (hotplug UX / #FW-43 soft-lock, `v1.2.5`):** после unplug/replug баннер
«выключите питание платы» + мёртвый Старт — soft false-lock: RX SHPROTO не
сбрасывался, `-inf` без retry, `POST /api/usb/recover` из httpd → reboot.
Фикс: RX reset на worker, retry `-inf` под `s_tx_mutex`, deferred teardown на
`usb_conn`, баннер + «Повторить связь», `last_shproto_ts_ms`. Soft recover не
заменяет VBUS edge на MCU спектрометра.

### #UI-43: тумблер шкалы X (с/м/ч) на «Мониторинге» не давал видимого эффекта

**Статус:** исправлен, прошивка [`firmware-v1.0.11`](https://github.com/VibeEngineering-LLC/atomspectra-waterfall-esp32/releases/tag/firmware-v1.0.11).

На графике «Мониторинг» переключатель единиц оси времени (секунды / минуты / часы) не
менял видимый шаг подписей — все три положения давали одинаковую сетку.

**Причина:** старый `xTickStep` (`web/monitor.html`) вычислял целевой шаг как
`target = spanMs/6`, игнорируя выбранную единицу — на реальном спане (напр. 199 мин) все

идентичной (`all_equal`).

**Исправление:** новый density-based `xTickStep` — целевая плотность тиков задаётся по
единице (`k = 15 / 8 / 4` для с / м / ч) на едином nice-list шагов; удалён guard-частокол
округления. Теперь с / м / ч дают три разных шага на любом спане.

**Проверка (2026-07-11):** на живой плате (`/api/system` fw=v1.0.11) на спанах 1 мин…12 ч
единицы дают `distinct=3` разных шага; на 199-мин спане с=900 с / м=1800 с / ч=3600 с →
13 / 7 / 3 тика (было — все одинаково).

### #FW-23: n42-экспорт — `StartDateTime` 1970 на каждой строке при автозапуске после ребута

**Статус:** исправлен в [`79eff24`](https://github.com/VibeEngineering-LLC/atomspectra-waterfall-esp32/commit/79eff24), в `main`. Прошивка `firmware-v1.0.1`.

### BUG-AS-07: Сборка падает на чистом клоне — undefined `spectrogram_is_recording`

**Статус:** исправлен в [`1b21d61`](https://github.com/VibeEngineering-LLC/atomspectra-waterfall-esp32/commit/1b21d61)

GitHub Actions job `build` (ESP-IDF v5.4) падал на чистом клоне репозитория за ~2 минуты.
Локально сборка проходила — баг проявлялся только на свежем clone (CI, чужая машина).

**Причина:** в публичный репозиторий попал **незавершённый фрагмент** функции
реконнекта USB. В `main/usb_host_cdc.c` (после восстановления CDC-соединения с прибором)
был вызов `spectrogram_is_recording()` — чтобы при активной записи водопада возобновить
набор спектра командой `-sta`. Сама функция определена в файлах подсистемы записи
водопада, которые на момент того коммита **не были закоммичены** (фича в незавершённой
локальной разработке). На машине автора всё компилировалось, потому что определение
лежало в рабочей копии; на чистом клоне компилятор видел только вызов без объявления →
`implicit declaration of function 'spectrogram_is_recording'`. В ESP-IDF действует
`-Werror=all`, поэтому implicit declaration — не предупреждение, а жёсткая ошибка сборки.

**Исправление:** незавершённый хук возобновления записи убран из `usb_host_cdc.c` в
публичном репозитории — сборка снова замкнута только на закоммиченные символы. Сама
функция автоматического возобновления набора спектра при реконнекте остаётся в
неопубликованной локальной ветке и будет внесена единым целостным коммитом вместе со
всей подсистемой записи водопада на диск (а не отдельным «висящим» вызовом).

**Обновление:** обещанный единый коммит внесён — подсистема автономной записи
сегментами (`spectrogram.[ch]`, эндпоинты `/segments` `/segment`, хук реконнекта в
`usb_host_cdc.c`, авто-возобновление через `spectrogram_restore()`) опубликована
целостно в ветке `rec-11-autonomous-recording`. Сборка на чистом клоне снова
самодостаточна — символ `spectrogram_is_recording()` теперь определён в составе того же
коммита, что и его вызов.

**Проверка:** CI job `build` на коммите `1b21d61` — зелёный (до этого `b0b8856` и
`958ac19` падали с тем же `implicit declaration`). Профилактика на будущее: перед push
ветку проверять «как чистый клон» — собирать только из закоммиченных файлов, а не из
рабочей копии с незакоммиченными изменениями.

### BUG-AS-06: Запись стрима водопада на диск самопроизвольно отключается

**Статус:** исправлен (см. `web/waterfall.html`, сериализатор записи `dskEnqueue`)

При активной записи водопада в файл («💾 Стрим на диск», формат `.aswf` через
File System Access API браузера) запись через некоторое время самопроизвольно
прекращалась — индикатор записи гас, файл переставал расти, хотя поток WebSocket
продолжал поступать. Воспроизводилось тем надёжнее, чем чаще приходили строки
(меньший интервал водопада); при больших интервалах — реже, но всё равно
систематически.

**Причина:** входящие WS-строки записывались в `FileSystemWritableFileStream`
вызовом `dskWritable.write(...)` **без `await`**, а каждые 30 секунд таймер
`flushDiskHeader` перезаписывал заголовок файла (ещё несколько `write()`).
`FileSystemWritableFileStream.write()` асинхронный: попытка начать новую запись,
пока предыдущая ещё не завершилась, бросает исключение **синхронно** (поток
заблокирован, `The stream is locked`). На стыке «запись строки данных ↔ перезапись
заголовка» исключение возникало систематически (примерно раз в 30 секунд); оно
ловилось обработчиком ошибок записи, который вызывал `stopDiskStream()` — поэтому
запись «сама» отключалась.

**Исправление:** все записи в поток сериализованы через единую Promise-очередь
(`dskEnqueue`) — следующая запись стартует только после завершения предыдущей, ни
одного конкурентного `write()`. Позиции записи заданы явными байтовыми смещениями
(`{type:"write",position:…}`) вместо неявного курсора: заголовок (позиции 0 и 8) и
строки данных (позиция ≥ `8 + резерв заголовка`) больше не пересекаются.
`stopDiskStream()` дожидается опустошения очереди (`await dskQueue`) перед финальной
записью заголовка и `close()`; добавлен реентранси-гард `dskStopping`.

**Проверка:** сборка прошивки (ESP-IDF v5.4) без ошибок; `node --check` встроенного
JS — без синтаксических ошибок; правка зеркально продублирована в демо
(`demo/waterfall.html`). Функциональный тест на плате: запись водопада с интервалом
5 с (строки приходят чаще, чем срабатывает 30-секундный флаш заголовка) — запись
держится без самоотключения.

### BUG-AS-05: Web UI обрушивается при многократном Ctrl+F5 (HTTP 431)

**Статус:** исправлен (см. `sdkconfig.defaults`, ключ `CONFIG_HTTPD_MAX_REQ_HDR_LEN`)

При многократной жёсткой перезагрузке (Ctrl+F5) страницы водопада интерфейс мог
обрушиться — часть ассетов не загружалась, графики/стрим переставали обновляться.

**Причина:** при жёстком reload браузер не использует кэш и шлёт запрос с полным
набором HTTP-заголовков (`Authorization: Basic` от web-auth + `Sec-Fetch-*` +
`Accept*` + `Cache-Control: no-cache`). Суммарный блок заголовков превышал лимит
ESP-IDF httpd `CONFIG_HTTPD_MAX_REQ_HDR_LEN` (по умолчанию **512 Б**), и сервер
отвечал `431 Request Header Fields Too Large` вместо страницы. Прошивка при этом
оставалась полностью стабильной (heap/CPU без изменений, без перезагрузок) —
обрушивался только UI в браузере.

**Исправление:** в `sdkconfig.defaults` подняты лимиты httpd:
`CONFIG_HTTPD_MAX_REQ_HDR_LEN=1024` и `CONFIG_HTTPD_MAX_URI_LEN=1024` (512 → 1024 Б).

**Проверка:** стресс-тест Ctrl+F5 с захватом UART — после фикса ответы `431`
исчезли (было: на каждый F5 → стало: 0), без перезагрузок прошивки, WS-реконнекты
проходят. Методика и сырые логи до/после: [`tests/stress/`](tests/stress/README.md).

## Ограничения

### Flash-память: износ при автосохранении

Автосохранение текущего спектра (`current.bin`, ~33 КБ) выполняется каждые 60 секунд. Это ~1440 записей в сутки.

| Тип flash-памяти | Ресурс | Оценка срока |
|---|---|---|
| Winbond (типовой, 100K циклов) | 100 000 стираний/сектор | **15–30 лет** |
| Дешёвый no-name (10K циклов) | 10 000 стираний/сектор | **1.5–5 лет** |

LittleFS использует copy-on-write и wear leveling по всему разделу (12.9 МБ), что распределяет нагрузку. При использовании оригинальных плат ESP32-S3-DevKitC-1 с Winbond flash проблем не ожидается.

**Возможные оптимизации** (не реализованы, не требуются при текущих сроках):
- Увеличить интервал автосохранения (например, 5 минут)
- Сохранять только при изменении спектра (delta-check)
- Хранить в PSRAM, писать на flash только при штатном выключении

### Один TCP-клиент

TCP-мост (порт 8234) поддерживает **одно** одновременное подключение. При попытке второго соединения оно будет отклонено. BecqMoni или AtomSpectra на ПК работают, пока не откроется второй экземпляр.

### ESP32 поддерживает только WiFi 2.4 GHz

Сети 5 GHz не поддерживаются аппаратно. Убедитесь, что роутер вещает на 2.4 GHz.

### #PERF-5: WiFi STA — modem sleep отключён (`WIFI_PS_NONE`)

По умолчанию ESP-IDF 5.4 в STA держит **MIN_MODEM** power save: на idle-плате это
даёт разброс ICMP/HTTP RTT в **десятки–сотни мс** практически без потери пакетов
(наблюдалось на плате #1, 2026-07-26). В `wifi_manager.c` после `esp_wifi_start()`
для STA выставляется `WIFI_PS_NONE` — RTT становится ровным.

**Trade-off:** выше потребление в STA-режиме; на питании от USB это приемлемо,
для автономного (батарейного) сценария режим стоит вернуть в `MIN_MODEM`.

Вызов не критичен для загрузки: при ошибке `esp_wifi_set_ps()` пишется
предупреждение в лог, плата продолжает работу на дефолтном энергосбережении.

### Web UI perf (`v1.2.2`, #PERF-1…4)

Под нагрузкой (браузер + AtomSpectra на ПК) ICMP-soak до платы давал
p50 ≈ 7.7 ms / **p95 ≈ 86.8 ms** / p99 ≈ 179 ms при 0% потерь — 9000 пакетов,
30 минут, прошивка `v1.1.2f`. После `v1.2.2`: p50 ≈ 5.1 ms / **p95 ≈ 60.3 ms** /
p99 ≈ 92.1 ms, RFC 3550 jitter 39.6 → 8.8 ms, потери по-прежнему 0%.
Единичный максимум при этом вырос (1.03 → 2.15 s, один сэмпл из 9000) — разбор
и полные данные в [`docs/perf1_report.md`](docs/perf1_report.md).

Оба замера снимались на сборках, где modem sleep уже отключён (`WIFI_PS_NONE`,
#PERF-5); `v1.1.2f` — приватная сборка «база + #PERF-5», тега в репозитории у неё
нет. #PERF-5 приходит отдельным изменением, поэтому на этой ветке **в
отдельности** modem sleep остаётся включённым по умолчанию и абсолютные числа
выше на ней не воспроизводятся. Воспроизводимой считаем дельту, не числа.

- **#PERF-1** — 2 с snapshot-кэш спектра (`spectrum_http_cache`): N вкладок = 1 render;
  hot path index = `/api/spectrum` + `/api/spectrum/meta.json`.
- **#PERF-2** — HEAVY lane (`http_io_gate`, concurrency=1): segment/window/export →
  503 + `Retry-After`; фронт `heavyFetch()`; autosave пропускается пока HEAVY busy.
- **#PERF-3** — waterfall `scheduleDraw()` / rAF coalesce (HiDPI без изменений).
- **#PERF-4** — спека async upload job API: `docs/spectrum-upload-job-api.md` (ещё не код).

### Автономная запись: кольцо keep-last при переполнении флеша не прошло длинный soak

**Контекст:** фича + фикс #WF-1 (`33fb4a4`) уже в `main`; ветка `rec-11-autonomous-recording`
как единое целое ещё не влита (лишние несвязанные коммиты сверху).

Автономная запись водопада сегментами (`seg_NNNNN.aswf`) и ротация сегментов при
достижении `WF_SEG_MAX_ROWS` (64 строки) **подтверждены** на плате: `seg_00000.aswf`
финализируется при заполнении и автоматически создаётся `seg_00001.aswf`.

Режим **keep-last ring** (при заполнении флеша затирается самый старый ещё не выгруженный
сегмент; счётчики `seg_count` / `seg_dropped`) реализован, но **не проверен длинным
soak-тестом** до фактического исчерпания раздела (≈763 строки, ≈5 суток при интервале
10 мин). До прохождения этого теста граница «флеш полон → перезапись старого» считается
непротестированной — этот конкретный сценарий (реальное исчерпание раздела) ещё не прогнан,
хотя сам код записи уже в `main`.

**Обновление 2026-07-04 (#STAB-2):** 9.40-часовой soak-тест записи через плату
подтвердил надёжность самой записи сегментов — **0 ребутов, 0 `seg_dropped`**, 52 чистых
`SEG_ROLLOVER` (см. фикс #WF-1 выше). Это не тот же тест, что soak до исчерпания
763-строчного раздела (кольцо keep-last по сегментам всё ещё не прогнано до реального
переполнения) — но попутно обнаружено **отдельное** ограничение экспорта: поле
`ring_capacity` в `/api/waterfall/status` фиксировано на **256 строк** (~4.25 ч при
кадансе ~60 с) — меньше, чем оценка ёмкости раздела (~763 строки) выше. При выгрузке
n42-экспорта запись длиннее ~4.25 ч оказывалась обрезанной — см. «#FW-19» в разделе
«Исправленные» (устранено в v1.2.28). Полный разбор: [`docs/stab2_report.md`](docs/stab2_report.md) §6.

Ограничение pull-опроса без пина сегмента (#REC-12) — тоже устранено в v1.2.28, см. раздел
«Исправленные».
