## Highlights

### Automatic spectrum backups on flash (issue #52)

When enabled, the gateway saves a snapshot of the current spectrum to LittleFS every Y hours
(`bk_<session>_<seq>.bin`) and keeps the last X of them, deleting the oldest first. **Off by default**
(`backup_keep` = 0); X is 1..20, Y is 1..168 h (default 24), both set on the "System" page or via
`/api/boot-config`. Snapshots appear on the "Saved" page as a separate group and export to XML, CSV
and JSON like manual spectra. Details and limits: `docs/spec-backup-52.md`, `KNOWN_ISSUES.md`.

### Acquisition watchdog: recovery after an instrument reboot

Before 1.2.23, after the instrument rebooted (for example via "Reboot instrument") acquisition stopped
while the page kept showing `USB:OK`. The USB-CDC link was not torn down, and the RX watchdog could
not see the silence: the FTDI bridge sends a 2-byte modem status continuously, and that refreshed the
RX timestamp the watchdog relies on. While stopped the instrument sends no histogram or status frames
(measured over 30 s on the bench), so "no SHPROTO traffic" alone cannot tell a stall from a stop.

Now the gateway remembers its own intent: a bare `-sta` → run, `-sto` → stop, `-sta` with parameters
(`-sta 60`, `-sta -s`) → unknown. "Reboot instrument" marks the intent as run beforehand if histograms
were arriving. If the intent is "run" and no histogram packet arrives for 20 s, it resends `-sta` (at
most once per 20 s). A single `-sta` is enough: no reconnect is needed. New fields in `/api/usb-diag`:
`acq_intent`, `acq_resend_count`, `last_acq_resend_ts_ms`, `last_hist_ts_ms`.

The watchdog stays silent after a user "Stop", after `-sta` with parameters, and after any traffic from
a TCP-bridge client (the AtomSpectra app) — until the gateway itself sends "Start" again.

### "Spectrum" page: Start/Stop show the acquisition state (#UI-44)

The button for the current state is dimmed and an indicator shows "● ACQ" / "○ stop", as on the
"Waterfall" page. The firmware has no explicit "acquiring" flag (`mode` does not change), so the page
uses the instrument's real-time counter in `meta.json`: it grows only while acquiring. After "Stop" the
page ignores growth until two consecutive frames without growth — cached frames still catch up for a
few seconds, and a threshold on the jump size flickered on real hardware.

## Known limitations (see `KNOWN_ISSUES.md`)

- **"Reboot instrument" wipes the accumulated spectrum.** The instrument clears its histogram and the
  gateway accepts the reset; backup snapshots (if enabled) and manually saved spectra survive. Save the
  spectrum manually first.
- The acquisition watchdog does not guard acquisition started by a TCP-bridge client, and stays off after
  any TCP-client traffic until the gateway sends "Start" again.
- If the "Spectrum" page receives no frames for more than 6 s, the Start/Stop state is shown as unknown.
- **Flashing `firmware.factory.bin` erases the settings partition (NVS).** The image is written from
  `0x0` and covers the `nvs` partition, so after an update the board starts in setup mode (WiFi must be
  entered again), boot settings return to defaults, and the waterfall segment counter `seg_seq` starts
  from 1 while older segments on flash keep their higher numbers. Segments already on flash are not
  touched. Collectors should not rely on `seg_seq` alone across a firmware update; match segments by file
  name and `started_at`. This applies to earlier releases as well; a fix is planned separately.
